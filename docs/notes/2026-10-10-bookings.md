## Routes

| Route | Who | Notes |
|---|---|---|
| `POST /bookings` | any signed-in | 201 + `BookingDto`. Runs `book_seat` as the user |
| `GET /bookings/mine` | any signed-in | own bookings only, newest first, course + payments + proofs joined |
| `GET /bookings/active` | any signed-in | held/paid, no joins. Parent: own. Teacher: own + bookings of courses they teach. Admin: all (Ruling 4) |
| `GET /bookings/:id` | owner | anyone else, unknown or malformed id: 404 `booking_not_found` |
| `GET /courses/:id/roster` | course teacher, admin | other teacher or parent: 403 `forbidden`; unknown course: 404 `course_not_found` |

## Decisions

- `book_seat` goes through a client built for each request: anon key plus `Authorization: Bearer <actor token>`, with no session persistence. The RPC reads `auth.uid()`, so all its rules still run in SQL: row lock, `course_full`, `registration_closed`, `already_booked`, `course_not_approved`, 7-day hold. A `P0001` exception becomes `DomainError(message)`.
- Reads use the service key. Each read is filtered by the scope the use case picks (owner id, taught courses, or all), so the API now enforces authorization where RLS used to (spec: "talks to the database with the service key").
- An empty or blank student name returns `400 student_name_required`, not a zod `Validation failed`. The route accepts any string and the use case trims and rejects it. A bad `courseId` still gets the zod 400 with a field error.
- `GET /bookings/active` returns raw held/paid rows. It does not drop holds that have lapsed. The pages keep calling `holdsSeat(b, now)` on the client, as they do today, so the "already booked" mark on a card goes away the second a hold runs out.
- Roster keeps the old RLS visibility (fix round 1, controller ruling). Teachers get the booking rows and student names only: `profiles.full_name` is `''`, `payments` and `payment_proofs` are `[]`. Before, profiles and payments were "own or admin" and payment_proofs "own or is_school_admin". An admin who is not admin01 also gets parent names and payments, but `payment_proofs: []`. admin01 also gets the proofs, each with `signed_url` (600 s). The use case maps the actor to a `RosterAccess` (`teacher` | `admin` | `school_admin`, `entities/booking.ts`). The repository then selects only those columns, so hidden data is never fetched.
- `profiles.full_name` is `''` when the viewer may not see it, or when the profile row is missing. The contract field cannot be null.
- If the read that follows a successful `book_seat` fails, the API answers 500 but the booking exists. A retry answers `already_booked`.

## Caveats

- `apps/frontend/src/adaptor/supabase/{my-bookings-gateway,course-roster-gateway}.ts` and their `interfaces/*` are still there but nothing in `deps.ts` uses them. The root cross-app test `tests/integration/frontend-backend-contract.test.ts` still imports the supabase `myBookingsGateway`. Delete them in Task 8/9 together with `lib/supabase.ts`.
- Pages are not migrated (Task 8). CoursesPage and TeacherPage still query `bookings` and call the `book_seat` RPC through supabase-js; they should switch to `loadActiveBookings` and `bookSeat`. ReceiptPage should switch to `loadBooking`. MyBookingsPage, AdminPage and PaymentsPage already go through the API via `loadMyBookings` and `loadCourseRoster`, so they need the API running (`task up`).
- `AppDeps` now requires `bookingRepository`. Tests that build `createApp({ frontendOrigin, authProvider })` with no group ports still pass at runtime, but `tsc` flags them, and the same is true for the other groups' ports.
