# Payments group (Task 6), 2026-10-10

## What was built

Backend (`apps/backend`)
- `entities/payment.ts`: `PROOF_TYPES` (jpeg, png, webp), `MAX_PROOF_BYTES` (5 MiB), `proofExtension`, `ProofFile`, `StoredProof`, `CourseSeats`, `RefundReport`, `PaymentOverview`.
- Ports: `interfaces/payment-repository.ts` (`ownBooking`, `proofOf`, `insertProof`, `replaceProof`, `confirmTransfer`, `courses`, `refunds`) and `interfaces/proof-storage.ts` (`upload`, `remove`). Every method takes the actor.
- `use-cases/payments.ts`: `createPayments({ paymentRepository, proofStorage })` returns `submitProof`, `confirmPayment`, `paymentOverview`, `refunds`.
- `adaptor/supabase/{payment-repository,proof-storage,payments-wiring}.ts`: every call runs with a user-scoped client (anon key plus the actor's bearer token, no session persistence, a new client per call). The service key is never used here, so RLS, the `payment-proofs` storage policies and `auth.uid()` inside `confirm_transfer_payment` behave exactly as they did in the browser.
- `adaptor/http/payments.routes.ts`, `adaptor/http/endpoints/payments.ts` (docs registry, four operations).
- Tests: `tests/unit/use-cases/payments.test.ts`, `tests/unit/api/payments.test.ts` (fakes in `tests/unit/payments-fakes.ts`), and `tests/integration/r2-payment.test.ts` (ported from direct supabase-js calls to HTTP; the `pay_booking` is `bank_transfer_only` check still calls the RPC directly).

Frontend (`apps/frontend`)
- `interfaces/payments-gateway.ts`, `adaptor/http/payments-gateway.ts` (`submitProof`, `confirm`, `overview`).
- `use-cases/submit-payment-proof.ts` (same type and size checks, same factory names) and `use-cases/load-payment-system.ts` now take the HTTP gateway. `app/deps.ts` wires them to it. Pages are not migrated (Task 8).
- `adaptor/http/client.ts`: a `Blob`/`File` body is sent raw with its own `type` as `Content-Type` (empty type: `application/octet-stream`); every other body is still JSON. The retry after a token refresh sends the same blob again.

## Routes

| Route | Who | Notes |
|---|---|---|
| `PUT /bookings/:id/proof` | owner of the booking | raw image body; booking must be `held` |
| `POST /bookings/:id/confirm-payment` | owner of the booking | idempotent once paid |
| `GET /admin/payments` | admin | `{ courses, refunds }`: `course_seats` rows oldest first, refund reports newest first |
| `GET /admin/refunds` | admin | refund reports newest first |

## Decisions

- Proof body: `express.raw({ type: ['image/jpeg','image/png','image/webp'], limit: '5mb' })`, mounted only on the proof route. The global JSON parser does not touch image bodies.
- Wrong content type: `proof_type_invalid` with HTTP **400** (not 415), so it goes through the shared error handler like every other rule failure. A JSON body counts as a wrong type.
- Body over 5 MiB: HTTP **413** `proof_size_exceeded` in the normal failure envelope. A route-level error handler in `payments.routes.ts` does this; `error-handler.ts` was not changed.
- Empty body (an accepted image type with 0 bytes): `payment_proof_required` (400). Nothing is stored.
- Order of checks: type, empty, size, then ownership (`booking_not_found`), then status (`booking_not_payable` when not `held`, including already paid). Nothing reaches storage before all of them pass.
- A path id that is not a uuid is `booking_not_found` (404), the same rule the courses routes use.
- Storage path stays `${userId}/${bookingId}-${uuid}.${png|webp|jpg}`. A second upload updates the same `payment_proofs` row (`proof_path`, `submitted_at`) and then removes the old object. If the lookup or write fails, the new object is removed and the error is rethrown. Removing objects is best effort, as in the old gateway.
- Errors that `confirm_transfer_payment` raises (`P0001`) become `DomainError(message)` (`booking_not_found`, `booking_not_payable`, `payment_proof_required`). Other database errors become a 500 whose log line has only the Postgres code.
- Admin reads check the role twice: in the route guard (`requireAuth(['admin'])`) and in the use case (`forbidden`).

## Caveats

- Existing tests that call `createApp({ frontendOrigin, authProvider })` fail `tsc` (TS2739) because `AppDeps` now needs `paymentRepository` and `proofStorage`. They still run, because the ports are only used when a payments route is hit. The payments tests cast their deps to `AppDeps`. A shared full-fake `AppDeps` helper would be the proper fix (see the courses note).
- The old `adaptor/supabase/payment-proof-gateway.ts`, `payment-system-gateway.ts` and their interfaces are still in place, because `tests/integration/adaptors.test.ts` uses them. They are no longer wired. Task 8 removes them along with supabase-js.
- MyBookingsPage maps every `DomainError` except `proof_type_invalid` to the size message. With the HTTP gateway, server codes such as `booking_not_found` also arrive as `DomainError`, so that page needs its error mapping fixed in Task 8.
- The API client's default timeout is 15 s for every request, uploads included. A 5 MiB proof on a slow link could time out.
- `docs/fern/openapi/openapi.json` has to be regenerated (`task docs:openapi`) for the new endpoints, and this note has to be listed in `docs/fern/pages/notes-index.mdx`. The docs group owns both files.
