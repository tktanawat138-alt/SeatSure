# 2026-10-11 CI/CD docs page

## What

Added the guide page `docs/fern/pages/ci-cd.mdx`: the `ci.yml` jobs and steps (unit, integration-e2e, docs, sonar), the
SonarQube setup (`sonar-project.properties`, `SONAR_TOKEN`, quality gate, scope), the manual local-to-Cloudflare release path
(`wrangler.jsonc`, `npm run deploy`, `VITE_API_URL`, `FRONTEND_ORIGIN`), three diagrams (pipeline, release path, a who-runs-what
table), a secrets table and troubleshooting. Everything was written from the workflow, the Sonar and Wrangler config and the
package scripts; nothing was run against GitHub or Cloudflare.

## Gaps found (documented as such, nothing fixed)

| Gap | Detail |
|---|---|
| No CD job | `ci.yml` never deploys. Cloudflare deploy is the manual `npm run deploy` in `apps/frontend`. An outline for a `deploy` job is on the page, marked not implemented. |
| No coverage upload | No coverage provider is installed (`@vitest/coverage-v8`), no lcov is produced, no `sonar.javascript.lcov.reportPaths`. This is why the quality gate is not awaited (`sonar.qualitygate.wait` stays false). |
| API and Supabase not hosted | Only the static frontend can be deployed; a deployed site has no API to call. Open roadmap item in the README. |
| `.env.local` leaks into a production build | `task up` writes `VITE_API_URL=http://localhost:3001` to `apps/frontend/.env.local`; Vite reads it in every mode, so `npm run deploy` without the variable in the shell bakes in localhost and `resolveApiBase` never throws. The check fires only when no env file sets the variable. |
| Leftover API after a failed cross-app step | In `integration-e2e` the `pkill` is the last line of the cross-app step. If `npm run integration` fails, the API keeps running and Playwright (`reuseExistingServer: false` in CI) may fail on port 3001. Not reproduced, read from the workflow. |
| Cloud script env paths differ | `cloud:seed` reads `.env.production.local` in `apps/backend`; `cloud:courses` reads `../../.env.production.local` (repo root). |
| Merge gating unknown | The jobs have no `needs`; whether red checks block merges is a GitHub branch protection setting not stored in the repo. PR decoration by SonarQube Cloud is likewise a Sonar-side setting. |

## Caveats

- The SonarQube Cloud dashboard URL is derived from the project key in `sonar-project.properties`.
- The default "Sonar way" gate is described from SonarQube's documented defaults, not from the project's actual gate.
